# Bug bash, 16 September 2026: the API, money, data and security

One of six runs going at the same time. This one is the API: `backend/src/api/`, `backend/src/payments/`,
`backend/src/lib/` and `backend/src/db/`, read for money that does not add up, for authorization that can be
walked around, and for data that can take a shop's booking path down.

**Checked.** `npm ci` at the root and in `backend/`. Baseline re-confirmed after resuming this run (checkout was
detached HEAD; reset local `main` to `origin/main` first): `npx tsc -b` clean at the root, 160 root tests,
`npx tsc -p tsconfig.json --allowImportingTsExtensions` clean in `backend/`, 132 backend tests, `npx vite build`
clean. Kept green before and after every change below.

**Found and fixed.**

- **An operator was promised a cent the transfer never sent** (`7cc77a56`). The booking email
  (`backend/src/api/bookingMail.ts`) and the Payouts page (`payoutOf` in `src/components/operator/OpMore.tsx`)
  worked the operator's net out in dollars, `price x 0.95` rounded to the cent, while the Stripe transfer
  (`splitBooking` in `backend/src/payments/money.ts`) took the 5% commission in whole cents. A half cent rounds
  the other way between the two, so over every price from $1.00 to $2,000.00 in cent steps the promise and the
  transfer disagreed 7,214 times, always by a cent and always with the promise above the money: $12.50 promised
  $11.88 and sent $11.87, $37.50 promised $35.63 and sent $35.62, and so on through $99.50, $112.50 and
  $187.50. `operatorShare` in `money.ts` is now the one rule, the commission rounded once in whole cents and the
  operator keeping what it leaves; `splitBooking`, `moneyOf` and `payoutOf` all go through it, the last through
  a matching `operatorNet` in `src/lib/pricing.ts`. `backend/src/payments/__tests__/operatorNet.test.ts` walks
  every price in that range and asserts the three name the same cent.

- **The admin gate leaked timing on every internal route but one** (`3a3b7328`). `POST /admin/payouts/run`
  already compared its key with `timingSafeEqual`; every other admin route (the outreach drafts, which carry
  live claim tokens) still compared with `===`, which gives up at the first wrong byte and leaks how much of a
  guessed key is right. Now the same length check plus `timingSafeEqual` guards all of them. With `ADMIN_KEY`
  unset the gate still refuses everything, unchanged.

- **A slow Postgres could wedge the whole API** (`75ea9b5e`). Nothing bounded how long a query could hold one
  of the pool's five connections. `select pg_sleep(12)` against a local cluster ran the full twelve seconds;
  five of those in flight held every connection, and a guest opening an unrelated listing waited the pool's
  fifteen-second connection timeout before getting a 500 for a database that was merely slow, not down. The
  pool now carries a ten-second statement timeout, a twelve-second client-side backstop, and a fifteen-second
  idle-in-transaction timeout (the last matters because `insertBookingChecked` holds a per-listing advisory
  lock for its transaction, so a connection stuck mid-transaction stopped every other booking for that shop
  too).

- **`POST /auth/request-code` timed out its own claim of being unprobeable** (`14142912e`). The comment said
  "the same answer either way, so this cannot be probed," but only the no-account branch actually returned
  right away. An address with an account made the route `await` a real send through Resend or Gmail SMTP
  before answering, so the response latency alone told a prober which addresses have an operator account, the
  exact thing the comment claimed was closed. The send is now fire-and-forget, like every other booking mail
  in the codebase, so both branches return in the same time.

- **A query that outlived its own client-side timeout could hand a wedged connection back to the pool**
  (`55c4ec92b`). `query_timeout` in `db/pg.ts` only gives up on the client's side; it never tells Postgres to
  stop, so a query that hits it (the backstop for a server that has actually stopped answering, not the
  ordinary slow-query case the statement timeout already ends) can leave the connection still waiting on a
  reply. `withTx`'s `finally { c.release() }` handed that connection straight back to the pool as if it were
  fine, so the next request to draw it inherited the same stuck wait, or a reply meant for a transaction that
  had already given up on it: the same "one slow connection wedges the pool" failure the statement and idle
  timeouts above were just added to close, one layer down. The rollback is still attempted; if it also cannot
  finish before its own timeout, the connection is now released with the error, which tells `pg-pool` to
  discard it instead of recycling it. Verified with a local `pg_sleep(20)` against the 10s statement timeout
  (the ordinary path) and by reading `node-postgres`'s own timeout handling for the pathological one, since a
  true network stall is not reproducible from this sandbox.
