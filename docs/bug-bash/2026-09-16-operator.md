**Found and fixed.**

- **One bad menu in a shop's saved record answered 500 to every booking** (`8eb6a7aaf`). The dashboard record is
  stored as the device sends it, so `options` and `addons` can be any shape at all. `POST /bookings` decided
  whether a shop had a menu by that field's length, and a string has a length, so a menu of `"oops"` got as far
  as `priceBooking`, which called `.filter` on it. Every booking for that shop answered 500: the guest saw
  "Something went wrong", the operator never heard about the request, and it stayed that way until somebody
  fixed the row by hand. Reproduced against the local Postgres, four shapes tried, one of them a 500 and two
  more quietly wrong. Both fields are read through one helper now that treats anything but an array as an empty
  menu, on the operator's patch and on the crawled listing file alike, so a malformed record costs the shop its
  prices, which already means pay on site, rather than its bookings. Two store-e2e checks cover it.
- **A shop that hid its listing was still taking bookings in the phone app** (`7618a258e`). The dashboard has two
  switches that stop bookings: Published off takes the page off the site, Accepting off leaves it listed and
  turns bookings away. The desktop listing page has read both since they were built. The listing in the phone
  frame, which is the same page a shared link, a booking email, Trips or a wishlist opens, read neither, so a
  guest whose link still worked got the whole picker: they chose a service, a date, a start time and a party,
  typed their name, mobile and email, pressed Request to book, and only then got a toast reading "This listing
  is hidden right now", with the booking refused and nothing to do next. Both flags reach a guest through the
  operator's published patch (`loadListing` calls `setOperatorOverride` with them), so this is every guest, not
  only the operator's own browser. The phone listing reads the same pair now and says which of the two it is;
  the bar at the bottom offers "Find another" in place of Reserve. One predicate, `bookingPaused`, so a third
  surface cannot pick up only one of the flags. Five tests.
- **An operator signed out a month ago went on editing a listing nobody could see** (`23cd37b99`). A dashboard
  session lasts thirty days and nothing renews it, and the claim link's own token expires too, so every operator
  who claimed a month ago reaches the day the API stops accepting their device. Nothing noticed: the profile save
  is debounced and fire-and-forget, so the 403 it came back with was thrown away, and the header went on reading
  "Saved", which is about this browser's storage and not about Outset. The owner fixed prices, changed hours and
  swapped photos and published none of it, while new booking requests stopped arriving in the feed at the same
  moment and just as quietly, because the poll behind it was being refused too. The three calls that carry an
  operator's credentials now say when the API refuses them, and the dashboard says so where the owner is working.
  Only 401 and 403 count, so a network failure is not mistaken for being signed out, and the demo dashboard,
  which has no session by design, stays quiet. Driven end to end in the rehearsal as the new step (j): the
  session is aged past its expiry, the business name is retyped, and the check is that the name at the API did
  not move and the dashboard said so. It fails on the old code.
- **One odd field in a request body answered 500 on six operator routes** (`bf4ce8bf0`). JSON can carry an object
  whose `toString` is a number, and `String()` throws on it. Found by probing every operator route with hostile
  input against the local Postgres: `POST /claims/:id/request` (name, email or phone), `/claims/:id/exchange`,
  both test bypass routes, `POST /auth/request-code`, `POST /auth/verify`, `PUT /profiles/:id` and
  `POST /bookings` all answered 500 rather than saying what was wrong. Body fields go through one helper now.
  An array is an object too, so a `patch` of `[1,2,3]` passed the profile write's check and was stored whole,
  then served to every guest opening that listing and to the nightly sync, both of which spread it over the
  catalog record as keys "0", "1" and "2".
- **Three things the dashboard told an operator that the product does not do** (`3e8cfd5d5`). Under every waiting
  request the booking drawer said "Declining sends the guest an automatic note offering your next open time".
  The decline email says the shop cannot take that time and links back to the listing; it offers no time, because
  nothing picks one. Email is also the only channel there is while the booking form asks for a name and a mobile
  and nothing else, so a guest who skipped the email box is told nothing at all, and a booking made in the same
  browser or a sample row is answered on the device and never reaches the API to be emailed. The Payouts page
  opened with "Guests pay by card when they book. An accepted booking is paid on your next pay day", three lines
  above its own card reading "Card payments and payouts switch on shortly. Until then guests pay you on site":
  card payments are switched on per API and the paragraph never asked. And the bar on the phone listing of a
  paused shop cut its second line off with an ellipsis.
- **Two NUL bytes made the store test file binary to git and grep** (`4e5fa3b18`). `scripts/store-e2e.mts` checks
  that a booking code with a NUL byte in it answers 404 rather than 500, and wrote that byte as a literal NUL
  inside `encodeURIComponent("...")`. Both tools read a NUL as the mark of a binary file, so the script was
  invisible to a search and every diff of it read "Binary files differ", on the one file a reviewer most wants
  to read on a change to the booking routes. Written as the `\0` escape, which is the same string at runtime.

**Also added to the rehearsal.** Step (c2b) opens a hidden listing in the phone app the way a guest does, since
step (c2) only ever read the desktop page, which is why the phone frame going on offering the whole picker was
never seen (`334f1377b`). Step (j) is the expired session above. The rehearsal is 52 steps, 0 failed.

**Found, not fixed.**

- **`GET /bookings/open/:listing` still offers times for a shop that is hidden or paused.** `openSlots` in
  `backend/src/api/openSlots.ts` reads the hours, the notice and the days off out of the dashboard record and
  never looks at `published` or `accepting`, so the picker route answers a full fortnight of start times for a
  listing whose own `POST /bookings` refuses every one of them. No guest sees it, because both listing pages now
  read the pause and never draw the picker, and the booking route is the gate that matters. Left alone because
  it is a behaviour change on a public route in the middle of six sessions working at once, and because the
  cases it would affect are ones no shipped client reaches.
- **The claim notice lands in the sidebar column.** `.odnotice` in `src/styles/operator.css` is not positioned,
  and `OperatorView` renders it as a direct child of `.od`, which is a two column grid whose `.odmain` is pinned
  to column two. So "This listing was already claimed by ..." auto-places into column one, under the fixed
  248px sidebar. It is the one thing a real owner is shown when somebody else walks in through a forwarded
  link. Read from the CSS and the markup rather than driven: nothing in the rehearsal claims a listing twice,
  so it was not reproduced in a browser and was left rather than guessed at. The signed-out panel this run adds
  is inside `.odbody` for that reason.

- **Editing two shops from one browser could lose the first shop's edit** (`42e089660`). `saveProfile`
  pushes every edit to the API through `saveRemoteProfile`, which debounces so a keystroke does not fire a PUT
  per character. The debounce was one shared slot for the whole module: `let queued: { id, body } | null`. Two
  businesses edited inside the same 1.2 second window silently collided: `applyStoredProfiles()`, which runs on
  every app load and loops over every business this device has claimed, called `saveRemoteProfile` once per
  business, and each call overwrote the last, so only the final business in the loop actually reached the API;
  the same thing happened if an owner of two shops used the sidebar's business switcher and edited the second
  one right after the first. The dropped shop's edit stayed on-device and the header still read "Saved," because
  that only reports the local write, but no guest and no other device ever saw it, and the next push would not
  happen until that shop was edited again. Fixed by keying both the pending timer and the queued body by listing
  id (two `Map`s instead of two module-level variables), so two businesses saving inside the same window each
  get their own PUT. `releaseRemoteProfile` updated the same way, so releasing one listing no longer reads the
  whole module's single slot. `saveRemoteProfile` and `import.meta.env`-gated `API_URL` mean this cannot be
  driven end to end under the plain `node --test` runner (confirmed: `API_URL` is `""` outside a Vite build, so
  the function no-ops), so the regression test reads the source the same way `authLost.test.ts` already does for
  a sibling bug in the same function, asserting the debounce state is a per-id `Map` and that neither function
  fell back to a shared slot. Two new checks in `src/lib/__tests__/twoShops.test.ts`. A concurrent run on this
  same file independently found and fixed the sibling half of the same root cause (`dc83bd649`, the signed-out
  notice firing for the wrong business when `applyStoredProfiles()` pushes every claimed shop on one load),
  which confirms the mechanism read the same way from both directions.
