**Found and fixed.**

- **One bad menu in a shop's saved record answered 500 to every booking** (`8eb6a7aaf`). The dashboard record is
  stored as the device sends it, so `options` and `addons` can be any shape at all. `POST /bookings` decided
  whether a shop had a menu by that field's length, and a string has a length, so a menu of `"oops"` reached
  `priceBooking`, which called `.filter` on it. Every booking for that shop answered 500: the guest saw
  "Something went wrong", the operator never heard about the request, and it stayed that way until somebody
  fixed the row by hand. Reproduced against the local Postgres, four shapes tried, one a 500 and two more
  quietly wrong. Both fields are read through one helper now that treats anything but an array as an empty menu,
  on the operator's patch and on the crawled listing file alike, so a malformed record costs the shop its
  prices, which already means pay on site, rather than its bookings.
- **A shop that hid its listing was still taking bookings in the phone app** (`7618a258e`). The dashboard has two
  switches that stop bookings: Published off takes the page off the site, Accepting off leaves it listed and
  turns bookings away. The desktop listing page has read both since they were built. The listing in the phone
  frame, which is the same page a shared link, a booking email, Trips or a wishlist opens, read neither, so a
  guest whose link still worked got the whole picker: they chose a service, a date, a start time and a party,
  typed their name, mobile and email, pressed Request to book, and only then got a toast reading "This listing
  is hidden right now", with the booking refused and nothing to do next. Both flags reach a guest through the
  operator's published patch, so this was every guest, not only the operator's own browser. The phone listing
  reads the same pair now and says which of the two it is; the bar at the bottom offers "Find another" in place
  of Reserve. One predicate, `bookingPaused`, so a third surface cannot pick up only one of the flags.
- **An operator signed out a month ago went on editing a listing nobody could see** (`23cd37b99`, scoped in
  `dc83bd649`). A dashboard session lasts thirty days and nothing renews it, and the claim link's own token
  expires too, so every operator who claimed a month ago reaches the day the API stops accepting their device.
  Nothing noticed: the profile save is debounced and fire-and-forget, so the 403 it came back with was thrown
  away, and the header went on reading "Saved", which is about this browser's storage and not about Outset. The
  owner fixed prices, changed hours and swapped photos and published none of it, while new booking requests
  stopped arriving in the feed at the same moment and just as quietly, because the poll behind it was being
  refused too. The three calls that carry an operator's credentials now say when the API refuses them, and the
  dashboard says so where the owner is working. Only 401 and 403 count, so a network failure is not mistaken
  for being signed out; the demo dashboard, which has no session by design, stays quiet; and the signal names
  the listing it is about, because a device pushes every business it has ever claimed on each app load and a
  session for one shop is refused for another by design.
- **Signing in with one shop's email signed the operator out of their other shop** (`94a24cb8c`). A claim link
  only ever goes to the address published on that business's own website, so an owner of two shops holds one
  address per shop. `POST /auth/verify` minted a session from the listings that one address owns and nothing
  else, and the app sent no session with the request, so there was nothing for the API to keep. The other shop
  stayed in the dashboard's business switcher, because that list is this device's own, and every save of it
  answered 403. It keeps what the caller already held now, the way `POST /claims/:id/exchange` and
  `POST /claims/:id` have since the fourth run, and the app sends the session it holds so there is something to
  keep. The prior session is verified and its expiry checked before anything is taken from it.
- **One odd field in a request body answered 500 on six operator routes** (`bf4ce8bf0`). JSON can carry an object
  whose `toString` is a number, and `String()` throws on it. `POST /claims/:id/request` on name, email or phone,
  `/claims/:id/exchange` on the token, both test bypass routes, `POST /auth/request-code`, `POST /auth/verify`,
  `PUT /profiles/:id` on the owner block and `POST /bookings` on the listing and on every field the cleaner
  touches all answered 500 rather than saying what was wrong. Body fields go through one helper now. An array is
  an object too, so a `patch` of `[1,2,3]` passed the profile write's check and was stored whole, then served to
  every guest opening that listing and to the nightly sync, both of which spread it over the catalog record as
  keys "0", "1" and "2".
- **The warning that somebody else claimed your listing was drawn behind the sidebar** (`c8277fb4d`). An operator
  whose claim link was forwarded, or who claimed from a second address, is shown one notice on the way in:
  "This listing was already claimed by ...". It was a direct child of `.od`, a two column grid whose `.odmain`
  holds column two, and `.odnotice` carries no placement of its own, so the grid auto-placed it into column one:
  measured in Chromium at 1440 by 900, x 8, width 248, y 764, which is a strip behind the fixed sidebar below
  the fold. In the phone frame `.od` is a flex column, so it sat under the tab bar instead. It renders at the
  top of the page body now, where the same element measures x 288, width 1112, y 90. No CSS changed.
- **A claim link that worked was called a bad link when the listing would not load** (`056d04048`). The claim
  screen reads the link, then waits up to a minute for the catalog and the listing's own file, which is where
  the token's hash lives. When it gave up it said the link did not check out and offered a fresh one, which is
  right for a token that really failed and wrong for the other way to get there. An owner in that state landed
  on a bare "Find your business" search box with nothing said at all, because the only message for a listing
  that did not resolve waits on the catalog reporting itself complete, which is the thing that had not
  happened. The splash behind it also sat on "Opening your dashboard…" for the whole minute, which reads like a
  page that has stopped.
- **Three things the dashboard told an operator that the product does not do** (`3e8cfd5d5`, and the Listing
  page's own line in `94a24cb8c`). Under every waiting request the booking drawer said "Declining sends the
  guest an automatic note offering your next open time". The decline email says the shop cannot take that time
  and links back to the listing; it offers no time, because nothing picks one. Email is also the only channel
  there is while the booking form asks for a name and a mobile and nothing else, so a guest who skipped the
  email box is told nothing at all, and a booking made in the same browser or a sample row is answered on the
  device and never reaches the API to be emailed. The Payouts page opened with "Guests pay by card when they
  book. An accepted booking is paid on your next pay day", three lines above its own card reading "Card payments
  and payouts switch on shortly. Until then guests pay you on site": card payments are switched on per API and
  the paragraph never asked. And the Listing page called an unpublished shop one "nobody can see or book",
  when a hidden listing keeps its own link working on purpose and a guest with a bookmark opens a page that
  says it is down.
- **Two NUL bytes made the store test file binary to git and grep** (`4e5fa3b18`). `scripts/store-e2e.mts` checks
  that a booking code with a NUL byte in it answers 404 rather than 500, and wrote that byte as a literal NUL
  inside `encodeURIComponent("...")`. Both tools read a NUL as the mark of a binary file, so the script was
  invisible to a search and every diff of it read "Binary files differ", on the one file a reviewer most wants
  to read on a change to the booking routes. Written as the `\0` escape, which is the same string at runtime.

- **Editing two shops from one browser could lose the first shop's edit** (`42e089660`). `saveProfile`
  pushes every edit to the API through `saveRemoteProfile`, which debounces so a keystroke does not fire a PUT
  per character. The debounce was one shared slot for the whole module: `let queued: { id, body } | null`. Two
  businesses edited inside the same 1.2 second window silently collided: `applyStoredProfiles()`, which runs on
  every app load and loops over every business this device has claimed, called `saveRemoteProfile` once per
  business, and each call overwrote the last, so only the final business in the loop actually reached the API;
  the same thing happened if an owner of two shops used the sidebar's business switcher and edited the second
  one right after the first. The dropped shop's edit stayed on-device and the header still read "Saved," because
  that only reports the local write, but no guest and no other device ever saw it, and the next push would not
  happen until that shop was edited again. Fixed by keying both the pending timer and the queued body by listing
  id (two `Map`s instead of two module-level variables), so two businesses saving inside the same window each
  get their own PUT. `releaseRemoteProfile` updated the same way, so releasing one listing no longer reads the
  whole module's single slot. `saveRemoteProfile` and `import.meta.env`-gated `API_URL` mean this cannot be
  driven end to end under the plain `node --test` runner (confirmed: `API_URL` is `""` outside a Vite build, so
  the function no-ops), so the regression test reads the source the same way `authLost.test.ts` already does for
  a sibling bug in the same function, asserting the debounce state is a per-id `Map` and that neither function
  fell back to a shared slot. Two new checks in `src/lib/__tests__/twoShops.test.ts`. A concurrent run on this
  same file independently found and fixed the sibling half of the same root cause (`dc83bd649`, the signed-out
  notice firing for the wrong business when `applyStoredProfiles()` pushes every claimed shop on one load),
  which confirms the mechanism read the same way from both directions.
