# Security review: keys, dependencies, workflows, and the API surface

Scope: secrets in git history and the working tree, dependency and supply-chain
hygiene in both `npm` trees, the GitHub Actions workflows, and the HTTP API
under `backend/src/api`. Two other sessions covered the site's rendering and
the crawler's trust rules; this pass assumes an attacker who can read the
public repository, the public site, and every public API response, and who
controls some of the websites the crawler visits.

This report is written incrementally: a section fills in as each fix lands.

## Checked

- Full git history (`git log -p --all`) and the current working tree for
  postgres/postgresql URLs with a password, GitHub tokens (`github_pat_`,
  `ghp_`, `gho_`), Stripe keys (`sk_live_`, `sk_test_`, `rk_live_`,
  `whsec_`), `sk-ant-`, `sk-proj-`, Resend/SendGrid/Postmark/SearchApi key
  shapes, and AWS access keys, plus generic `KEY`/`SECRET`/`TOKEN`/`PASSWORD`
  assignments next to a long literal value.
- No live-looking secret of any of those kinds was found, in history or
  in the working tree. A handful of pattern hits turned out to be
  coincidental substrings in scraped JSON (a booking policy string, an
  S3 presigned-URL access key ID that belongs to an operator's own
  bucket, not Outset's) and two placeholder values in test files
  (`e2e-local-claim-secret`, `whsec_test_verifyWebhook`).
- `.gitignore` coverage for `.env`, `.env.*`, `backend/.env`, and local
  database files.
- `render.yaml` and `.github/workflows/*.yml` for hardcoded credential
  values (all secrets are `sync: false` or `${{ secrets.* }}`).
- `npm audit` in both trees, with and without `--omit=dev`.
- Both `package-lock.json` files are committed; every CI workflow and
  `render.yaml` build step, install script.
- Whether any dependency resolves outside the npm registry (git URL or
  tarball).
- Versions of the packages hit by the September 2025 npm supply-chain
  incidents (`chalk`, `debug`, `ansi-styles`, `strip-ansi`, `ansi-regex`,
  `wrap-ansi`, and related color/ansi packages) against the known-bad
  versions: every one resolved in the lockfiles is a version released
  after the incident, none of the compromised versions are present.
- Every installed package that declares a `preinstall`, `install`, or
  `postinstall` script: only `esbuild`'s own standard `postinstall`
  (`node install.js`, which selects the platform binary) in either tree.
  No other package runs an install-time script.
- Both `package-lock.json` files are committed, and every CI workflow
  and Render build step uses `npm ci`, never `npm install`.
- Whether any dependency resolves outside the npm registry: every
  `resolved` URL in both lockfiles points at `registry.npmjs.org`, none
  is a git URL or an external tarball.
- Every workflow under `.github/workflows` for a top-level or job-level
  `permissions:` block, third-party actions pinned to a SHA, secrets
  echoed to a log or artifact, `pull_request_target` combined with a
  checkout of the PR head, and whether the payout and backup workflows
  can run outside a schedule or a collaborator's manual dispatch.
- No workflow in this repository uses `pull_request` or
  `pull_request_target` at all, so there is no path from an external
  PR into a workflow that has secrets or push access.
- `pay-operators.yml` and `db-backup.yml` only trigger on `schedule` and
  `workflow_dispatch`; GitHub only lets a collaborator with write access
  invoke `workflow_dispatch`, so both were already correctly gated.
- Whether `BRAVE_SEARCH_API_KEY`, `E2E_DATABASE_URL`, or any other
  workflow secret is ever printed to a log or written into an uploaded
  artifact: none of the scripts that use them
  (`discover-florida-ci.mts`, `braveapi.ts`, `e2e-local.mts`,
  `store-e2e.mts`, `payout-e2e.mts`) log the secret itself, only
  whether it is set, and the only error message logged from a failed
  Postgres connection (`backend/src/db/pg.ts`) is `error.message`, which
  node-postgres does not fill with the connection string.
- Every route file under `backend/src/api` (`auth.ts`, `profiles.ts`,
  `claims.ts`, `bookings.ts`, `payouts.ts`, `uploads.ts`, `webhooks.ts`,
  `unsub.ts`, `availability.ts`), and the shared helpers in
  `backend/src/lib` (`claim.ts`, `repo.ts`, `unsub.ts`, `claimIndex.ts`,
  `mail.ts`) and `backend/src/db/pg.ts`, read end to end against the
  checklist below.
- Security headers, CORS, the JSON body limit, the admin gate, and
  `/health` were also driven live: started the real server
  (`src/serve.ts`) against a local Postgres and curled it. Confirmed
  live: `x-frame-options: DENY`, `permissions-policy`,
  `x-content-type-options: nosniff`, `referrer-policy: no-referrer`,
  `strict-transport-security`, and `cache-control: no-store` on every
  response; `access-control-allow-origin` echoes back only for
  `https://onoutset.com`, never for an arbitrary `Origin` header; a
  request over 2 MB gets `413`; `/taxonomy/categories` (behind the
  admin gate) answers `404` with no `ADMIN_KEY` set, whether or not the
  caller sends an `x-admin-key` header; and `/auth/request-code` allows
  exactly 20 requests an hour from one caller before answering `429`.
- Every mutating route (`POST`/`PUT`/`PATCH`/`DELETE`) in `auth.ts`,
  `profiles.ts`, `claims.ts`, `bookings.ts`, `payouts.ts`, `uploads.ts`,
  `webhooks.ts`, and `unsub.ts` carries a `rateLimit(...)`. The mutating
  routes in `routes.ts` with none (`/contacts/sync`, `/targets`,
  `/ingest/tampa`, `/scrape`, `/scrape/one`, `/outreach/generate`) are
  all registered after the admin-key gate, so they are not reachable
  without `ADMIN_KEY` in the first place; they are not the
  "unauthenticated write" the checklist means.
- Every `db.prepare(...)` and `query(...)` call across `backend/src`
  for string-built SQL: every value a caller can influence goes through
  a `?` or `$1`-style placeholder. `routes.ts`'s `/operators` handler
  builds its `WHERE` clause by string concatenation but only ever
  appends fixed, hardcoded clause text (`" AND metro_id = ?"`), never a
  request value.
- `backend/src/db/pg.ts` connects with `ssl: { rejectUnauthorized:
  true }`, unconditionally, not read from the connection string. Built
  a real local Postgres 16 instance under `/tmp` with a self-signed
  certificate and TLS required (`apt`'s postgresql-16 was already
  installed), combined that certificate with `/root/.ccr/ca-bundle.crt`
  into `NODE_EXTRA_CA_CERTS`, and confirmed both directions: `pg`
  connects when the certificate is trusted, and fails with
  "self-signed certificate" when it is not, so this is a real,
  effective check rather than a flag that is set but never enforced.
- Ran `backend/scripts/store-e2e.mts` and `backend/scripts/payout-e2e.mts`
  against that same local, TLS-verified Postgres (`E2E_DATABASE_URL`
  pointed at it): both printed "All ... checks passed", which drives
  claim exchange, profile writes, sign-in codes, bookings, payouts, and
  listing release through the real routes and the real database, not a
  mock.
- The claim token and session design in `backend/src/lib/claim.ts` and
  `backend/src/api/auth.ts`: 256-bit `CLAIM_SECRET`, HMAC-SHA256
  signing, timing-safe comparison on every check (claim tokens,
  sessions, sign-in codes, the admin key, the Stripe and Resend webhook
  signatures), and v2 claim links that carry and sign their own expiry
  so it cannot be extended by editing the link.
- What holding the public `claimKey` in `public/o/<id>.json` alone
  would let someone do: it is `sha256(claimToken(id))`, a one-way hash.
  `mayEdit()` hashes whatever the caller sends and compares that to the
  same value, so producing a match still needs the raw token from a
  claim email; the public hash cannot be replayed as if it were the
  token. Knowing it does not advance a claim or a sign-in.
- Whether the Stripe webhook (`POST /stripe/webhook` in `bookings.ts`)
  can be replayed: `verifyWebhook` in `stripe.ts` checks the signature
  and rejects a timestamp more than 10 minutes old, and, independently
  of that, the handler's own state machine only acts on a booking whose
  status is still `"pending"` (`updateBooking`, under a Postgres row
  lock), so a second delivery of the same event, in or out of that
  window, finds the booking already moved on and changes nothing. This
  is not the textbook "have we seen this event id before" table, but it
  is an equivalent guarantee here: replay is a no-op, not a double
  charge or a double notification.
- `GET /profiles/:id` and `GET /listing-edits` in `profiles.ts`: the
  first returns the owner block only when the caller's claim token or
  session already proves they may edit that listing, otherwise only
  `{id, published, patch, updatedAt}`; the second
  (`listProfileEdits` in `repo.ts`) never selects the owner column at
  all. Neither leaks who owns a listing to an unauthenticated reader.
- `GET /health` no longer returns anything Render's own health check
  or the e2e harness reads (see fix below); nothing else served by this
  API answers with a hostname, a stack trace, a SQL fragment, or a file
  path (`payouts.ts` and `bookingMail.ts` truncate third-party error
  messages to 160-300 characters before they reach a client, and the
  photo upload route's own comment explains why: "Every screen prints
  the API's own `error` straight onto the operator's toast, so this has
  to be written for them").

## Found and fixed

- **7fde66e6d** - `backend/data/outset.corrupt.db` and
  `backend/data/outset.recovered.db`, two SQLite dumps from a past crash
  recovery (113 MB total), were committed to the repository. They hold the
  same operator data already public in `public/catalog.json`, so this was
  not a credential leak, but it broke the rule in `backend/data/AGENTS.md`
  ("outset.db is local SQLite. Do not commit it") and left a large binary
  blob in every future clone. Untracked both files and widened
  `.gitignore` from the single `outset.db` name to `backend/data/*.db`
  (and `-wal`/`-shm`), so any future local SQLite file, crash dumps
  included, stays out of commits by default.

- **836498bf4** - Neither tree had an outstanding known vulnerability
  (`npm audit` was clean before and after, with and without `--omit=dev`),
  but several packages (`react`, `@types/react`, `@types/react-dom`,
  `@neon/config`, `@neon/env` at the root; `hono`, `nodemailer`, `openai`,
  `zod`, `@types/node`, `@types/nodemailer` in `backend/`) had newer
  releases inside their existing `package.json` ranges. Ran `npm update`
  in both trees so the lockfiles pick those up before they drift further.
  No range or major version changed. `tsc`, both test suites, and the
  `vite` build stayed green before and after.
- **00cc1ad3d** - Nothing watched for new dependency or GitHub Action
  releases, so a fix for the next supply-chain incident would only be
  found by hand. Added `.github/dependabot.yml`: weekly npm updates for
  the root app and `backend/`, minor and patch changes grouped, major
  bumps ignored, plus weekly updates for the actions used in
  `.github/workflows`.
- **f80ad59c8** - Every workflow referenced `actions/checkout@v4`,
  `actions/setup-node@v4`, `actions/upload-artifact@v4`, or
  `actions/download-artifact@v4` by a mutable tag. If that tag were ever
  repointed (upstream, or by a compromised maintainer account, the same
  pattern as the September 2025 npm incidents this review checked for)
  every one of the eight workflows would run the new code on its next
  scheduled trigger, several of them with `contents: write` and push
  access to `main`, with nothing to review first. Pinned every one to
  the full commit SHA of its current `v4` release, version kept in a
  trailing comment. Also gave every workflow or job that was running on
  the default `GITHUB_TOKEN` scope an explicit `permissions:` block:
  `contents: read` where a job checks out code but never pushes,
  `permissions: {}` where a job only calls `curl` (`keep-warm.yml`,
  `pay-operators.yml`) and never checks out the repository at all. The
  jobs that push (`discover-florida`, `photo-screen`, and the `collect`
  jobs in `photo-crawl` / `structure-crawl`) already declared
  `contents: write` and are unchanged.
- **33b8df6a8** - Two log lines printed a guest's or operator's raw
  email address on the server: the mail-send failure line in
  `bookingMail.ts` (once per rejected send, so a run of bounces wrote
  real addresses into the log repeatedly) and the no-`RESEND_API_KEY`
  dry-run line in `mail.ts`, which already redacted sign-in codes and
  claim links but not the address itself. Both now go through the
  `maskEmail()` helper the claim routes already use
  (`i...@example.com`), confirmed live during the local Postgres run
  above (`[mail:dry] to=s...@e2e-store.example ...`).
- **019c34e80** - Three gaps in the app-wide middleware in
  `routes.ts`: the CORS allowlist's fallback (used only when
  `ALLOWED_ORIGINS` is unset; Render always sets it) named
  `https://harshils2340.github.io`, a GitHub Pages origin nothing in
  the app serves from, so removed it, leaving only `onoutset.com` and
  the local dev ports. Every response got `nosniff`, `referrer-policy`,
  `cache-control`, and HSTS, but never `X-Frame-Options` or
  `Permissions-Policy`; added `X-Frame-Options: DENY` and a
  `Permissions-Policy` that switches off geolocation, camera,
  microphone, and payment. `GET /health` returned a commit hash
  (`RENDER_GIT_COMMIT`) alongside service and store labels to any
  unauthenticated caller, letting an attacker match a live deployment
  to a known-vulnerable commit; reduced to `{"ok": true}`. All three
  confirmed live against the running server (see the header and
  `/health` probes above).

## Found, not fixed

- Sessions (`Session` in `backend/src/api/auth.ts`) are stateless,
  HMAC-signed tokens: `verifySession` only checks the signature and the
  embedded expiry, never whether the listing it names is still claimed.
  `DELETE /profiles/:id` and `POST /claims/:id/test-unclaim` both
  delete the profile row and unlink every email that could sign in to
  it, which is what "claimed" means on this side, but neither
  invalidates a session already issued for that listing. A session
  minted before a release stays valid, and therefore able to reclaim
  and re-edit that listing through `PUT /profiles/:id`, for up to its
  full 30-day life, exactly the scenario `backend/AGENTS.md` describes
  the v2 claim-link redesign as being about ("one forwarded email or
  screenshot could claim that business forever"). A real fix needs the
  session to carry, and `mayEdit` to check, some value that changes
  when a listing is released or re-claimed (its `claimedAt`, or a
  per-listing counter), which means an async lookup inside `mayEdit`
  where there is none today and changes to every place a session is
  minted (`auth.ts`, `claims.ts`, `profiles.ts`). That is a real change
  to the session format, not a one-line patch, and backend/src/api is
  also where the bug-bash session on this branch is actively working,
  so it is left for a dedicated pass rather than attempted here under
  time pressure. Exactly where: `verifySession` and `mayEdit` in
  `backend/src/api/auth.ts`.
- The legacy, non-expiring claim token (`claimToken` /
  `verifyClaimToken`'s `legacy` branch in `backend/src/lib/claim.ts`)
  is still accepted alongside the v2 expiring one, on purpose, so links
  already sent keep working; `backend/AGENTS.md` already documents this
  and says to drop the branch "once nothing old is in circulation."
  Left alone: that is a product decision about how long old outreach
  stays honored, not a bug, and it is already tracked. Listed under
  Needs Harshil below as something only Harshil can decide the timing
  of.

- The 113 MB of SQLite data from the commit above (`bf4ce8bf0`) is still
  reachable in git history. Removing it fully needs a history rewrite
  (`git filter-repo` or equivalent) and a force-push, which this review
  will not do on a branch six other sessions are actively pushing to. A
  clean-up pass with everyone stopped is a job for Harshil to schedule
  separately.

## Needs Harshil

- **Branch protection on `main`.** Six sessions are pushing straight to
  `main` right now with no review gate. At minimum, require the status
  checks this review depends on (`tsc`, both test suites, the `vite`
  build) before a merge, once the workflow that runs them on every push
  exists; today they only run locally, per session.
- **Two-factor authentication** on GitHub, Render, Neon, Stripe, and
  the mail provider (Resend), if not already on.
- **Turn on Dependabot alerts and secret scanning** in the repository
  settings (Settings -> Code security). `.github/dependabot.yml` now
  schedules version-update PRs, but that is a different setting from
  the alerts and push-protection GitHub runs itself.
- **Stripe**: confirm the key in use is a restricted key scoped to only
  what `backend/src/lib/stripe.ts` and `payouts.ts` call (checkout
  sessions, payment intents, transfers, Connect accounts), not a full
  secret key, and that `STRIPE_WEBHOOK_SECRET` matches the endpoint
  actually registered for `/stripe/webhook`. Rotate `STRIPE_SECRET_KEY`
  and `STRIPE_WEBHOOK_SECRET` if either has ever been shared outside
  Render's dashboard.
- **Neon**: rotate the `DATABASE_URL` password on a schedule (this
  review found no evidence it has leaked, but it has also never been
  rotated as far as git history shows).
- **The GitHub PAT** (`GITHUB_TOKEN` in `render.yaml`, used by
  `uploads.ts` to commit photos): confirm its scope is limited to this
  repository's contents and that it has an expiry set, not "no
  expiration."
- **Render environment check**: confirm `OUTSET_TEST_CLAIM_EMAILS` is
  not set on `outset-api` or any other Render service. This review
  could not check the live Render dashboard from this sandbox (no
  production credentials, by design); `render.yaml` correctly omits
  it, but `render.yaml` is only the template Render was last synced
  from, not a live read of what is actually set.
- **Decide when to drop the legacy, non-expiring claim token** in
  `backend/src/lib/claim.ts` (see "Found, not fixed"). It only affects
  links sent before the v2 token existed.
- **The session-revocation gap** in "Found, not fixed" above: worth a
  dedicated pass once the other bug-bash sessions are done with
  `backend/src/api`, since the fix touches the same session-minting
  code they may also be editing.
- **The 113 MB of SQLite history** in "Found, not fixed": a
  `git filter-repo` pass to actually shrink the repository needs
  everyone to stop pushing first, since it rewrites every commit hash
  after the one it removes.
